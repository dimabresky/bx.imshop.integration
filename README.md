# bx.imshop.integration

Webhook-и IMSHOP Retail Protocol для интернет-магазина 1C-Bitrix.

Origin: `https://github.com/dimabresky/bx.imshop.integration.git`.

Модуль размещается в `local/modules/bx.imshop.integration` и может подключаться как git submodule. Установка копирует `install/imshop/` в `/local/imshop/`. Удаление модуля удаляет этот каталог.

Ключ передаётся заголовком `Authorization: Bearer <key>` или полем `key` в JSON. Ключ задаётся в настройках модуля после установки и в репозиторий не попадает. Пустой ключ закрывает endpoint.

Вкладка «Статусы» в настройках модуля хранит сопоставление статуса IMSHOP со статусом заказа Bitrix и текст сообщения при смене статуса в таблице `b_bx_imshop_order_status`. Тот же справочник читают входящая смена статуса и исходящая отправка в IMSHOP.

## Реализованные webhooks

Список пополняется при добавлении endpoint.

- `POST /local/imshop/deliveries` — расчёт способов доставки. Временный заказ Sale не сохраняется. Цена и пункты самовывоза совпадают с `bitrix:sale.order.ajax`. Службы из опции «Службы доставки ПВЗ» тоже отдаются как самовывоз. Опция «Только склады со всеми товарами» оставляет в штатном списке склады, где свободного остатка хватает на всю корзину. После складов модуль вызывает событие `onPickupLocationsBuild`. Если в запросе есть `addressData.lat` и `addressData.lon`, в ответ попадают до 10 ближайших точек в радиусе 10 км.
- `POST /local/imshop/payments` — список способов оплаты. Временный заказ Sale не сохраняется. Состав совпадает с ограничениями `bitrix:sale.order.ajax` для выбранной доставки.
- `POST /local/imshop/payments/create` — создание оплаты картой bePaid (`command: create`). Заказ уже оформлен. Ответ содержит токен checkout как `paymentId`, URL оплаты bePaid и регулярные выражения возврата из настроек платёжной системы. Повторный запрос возвращает тот же checkout, пока он не отклонён. После отказа создаётся новый платёж Bitrix: штатный обработчик bePaid не меняется и различает попытки по id платежа. Уже оплаченный заказ новый checkout не создаёт.
- `POST /local/imshop/payments/check` — проверка списания (`command: capture`). Статус читается в bePaid по токену checkout. При успехе и совпадении суммы платёж помечается оплаченным, если в платёжной системе включено «Изменять статус оплаты после оплаты». Пока статус не финальный, ответ содержит `pending: true`.
- `POST /local/imshop/orders/status` — смена статуса из приложения. `id` — id заказа Bitrix, как в ответе оформления; если такого id нет, ищется `ACCOUNT_NUMBER`. `status` — код IMSHOP из вкладки «Статусы». Для `canceled` заказ ещё и отменяется, причина пишется в `REASON_CANCELED`. Несопоставленный код и неизвестный заказ заказ не меняют. Когда статус меняет сайт, модуль отправляет его на URL из настроек с заголовком `app-locale: ru`, если URL задан и начинается с `https://`. Пустой URL отправку выключает. Если одному статусу Bitrix сопоставлено несколько кодов IMSHOP, уходит первый из списка кодов.
- `POST /local/imshop/orders/history` — история заказов покупателя. `userIdentifier` — id пользователя. Страница по 20 заказов, новые сверху. `nextPage` есть только когда следующая страница не пустая. Неизвестный пользователь отвечает пустым `orders`.
- `GET /local/imshop/stores` — карта магазинов, JSON-массив без тела. Элементы инфоблока из опции «Инфоблок магазинов». Пустая опция отвечает `[]`.
- `POST /local/imshop/orders/create` — оформление заказа. Корзина пересчитывается Sale, заказ сохраняется. Повтор с тем же `uuid` возвращает уже созданный заказ. Цены из запроса, бонусы и флаг `paymentProcessed` не применяются. Подарок, который всё ещё даёт правило корзины, сохраняется с нулевой ценой. Покупатель берётся из `externalUserId`. Если id нет, заказ привязывается к пользователю с этим телефоном. Если пользователя нет, создаётся активный из имени, телефона и email. Без телефона заказ не оформляется.
- `POST /local/imshop/availability` — проверка наличия. `configurationIds` — id элементов каталога из YML. В ответе склады сайта и свободный остаток (`AMOUNT` минус резерв). Пункт выдачи отдаётся как магазин своего города, склад отгрузки без выдачи — как интернет-склад для любого города. Цена совпадает с YML-фидом.
- `POST /local/imshop/otp` — запрос SMS-кода. Номер ищется в phone auth и в телефонах профиля. Существующему пользователю уходит штатный код Bitrix. Если номера нет и в запросе нет `fullName`, ответ `dataRequired` только с `fullName`. Email, дата рождения и пол сохраняются, когда они уже есть в запросе. Повтор с ФИО в порядке «фамилия имя отчество» создаёт неактивного пользователя и отправляет код. Повтор внутри минуты новую SMS не шлёт. Юрлица и согласия не сохраняются.
- `POST /local/imshop/otp/confirm` — проверка кода. Верный код активирует нового пользователя и возвращает `user` (`id`, имя, телефон, email, пол, возраст, дата рождения, бонусы Aspro и уровень, если они есть). Сессия Bitrix не открывается. Неверный код и исчерпанные попытки приходят как `error.message`.
- `POST /local/imshop/users` — профиль по `userIdentifier` (id пользователя из `user.id` после входа). Ответ — тот же объект `user`. Неактивный и неизвестный id приходят как `error.message`.
- `PATCH /local/imshop/users/update` — правка имени, телефона, email и даты рождения. Обновляются только поля, которые есть в JSON. Ответ — полный `user`. Чужой телефон не записывается. Юрлица, согласия и бонусы из запроса не сохраняются.
- `POST /local/imshop/users/otp` — SMS на номер из `phone` для уже существующего пользователя. Пользователь не создаётся. Повтор внутри интервала Bitrix новую SMS не шлёт. Код хранится в кэше и не меняет телефон входа.
- `POST /local/imshop/users/otp/confirm` — проверка этого кода. Верный код отвечает `success: true` и не открывает сессию. Неверный код отвечает `success: false` и строкой `error`.
- `POST /local/imshop/basket` — пересчёт корзины. Временный заказ Sale не сохраняется. Цены и скидки совпадают с правилами корзины сайта: купон из `promocode`, пользователь из `externalUserId`. В итог входят только отмеченные доступные позиции, без доставки и без вычета бонусов. Если у покупателя есть бонусы Aspro, в ответе `bonuses.canSpend` — максимум к списанию; баланс при этом не меняется. Отложенные позиции не двигают порог правила. Подарки правил Bitrix приходят в `promoGroups`: `all` сразу строками с `gift`, `one` как `giftOptions`, выбранный подарок — по `promoGroup`. Подарочные карты не применяются.
